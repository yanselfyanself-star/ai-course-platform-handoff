技术选型建议（具体落地，免费优先）

1. 文案生成 —— DeepSeek API

走 v2 已有的 EngineRegistry 接缝，把 DeepSeek 当一个“文案 Provider”接：base_url + api_key 写进 Provider.config_json，绝不硬编码；未配置时自动降级到“本地规则改写/手动编辑”，保证离线也能用。提示词模板沉淀为可编辑资产（标题优化、钩子库、口播口语化三件套）。

2. 链接提取 —— 视频号 / 抖音 / 小红书（免费优先）

平台推荐方案成本说明
抖音 / 小红书yt-dlp 下载视频 → 本地 Whisper 转写文案免费开源公开 Web 可抓；注意频率与平台 ToS，做本地限速
视频号粘贴文案 + 本地 Whisper 转写（用户既定决策）免费视频号封闭，自动化提取不稳；走“粘贴 + 本地转写”插件式自研
原则：免费优先、本地优先、不依赖厂商网关。转写统一走本地 Whisper，与“链接提取去厂商化”项目一致。

3. 声音克隆 + 多音字 —— 直接复用 V1 已验证资产

V1 真机验证过的链路不要重造：POST /api/voice/clone（body {"prompt_audio": "本地路径"}）→ IndexTTS2 → 落 VoiceModel → 返回 voice_id；之后 TTS 以 voice_id 引用。多音字修正保留 V1 能力（字级拼音标注 + 人工/规则校对），这是甲方明确要求的硬功能。迁移方式：经 v2 的 TTS/Voice Provider 接入，复用既有接口。

4. 口型渲染 —— KrLongAI（契约已固化，照抄 v1）

直接按 docs/research/KrLongAI渲染契约.md 经 v2 LIPSYNC Provider 接入。v2 engines/lipsync.py 当前是“引擎无关通用适配器”，已兼容 urlData 与嵌套 data.data 进度解析，只需补 2 处差距：

差距要改什么
① 提交 body 字段映射把通用 body 改为 KrLongAI 契约：audio_file / type:"sync" / meta_human_name:"vid_{id}.mp4"（必带 .mp4）/ video_file_name / use_super_resolution:false / batch_size:8；code!=0 即拒
② 算法就绪前置提交前调 POST /algorithm/start/（body {"type":"video_sync"}）并轮询 GET /algorithm/status/ 直到 video_sync_status=="open"，否则会 code:-1
⚠ 决策冲突：此前战略定过“KrLongAI 保持不动（Q3/Q4 不处理，核心渲染厂商不动）”。而本次新需求明确“口型渲染走 KrLongAI”。这是方向级冲突，需甲方拍板（见④）。

待甲方拍板的决策点

决策 1：口型渲染是否正式启用 KrLongAI？
新需求要求“影像说话”走 KrLongAI，但此前战略说“核心渲染厂商保持不动”。若启用，需补 2 处适配器差距（约 1~2 天，非重造）；若维持不动，则“单主体真人数字人”核心卖点无法落地。请阎先生/PM Hermes 确认。

决策 2：视频号提取走“粘贴+本地 Whisper”还是投入自动化抓取？
自动化在视频号上不稳且易触发风控；本地粘贴+Whisper 免费、合规、已是你方既定决策。建议维持本地方案，把精力放在抖音/小红书（yt-dlp 可用）。

决策 3：5 环节是否一次性全做，还是按 M 里程碑分期？
建议分期：M-A 先把“对话 UI + ①文案 + ②配音克隆”跑通（资产已具备）；M-B 再补“③口型（待决策1）+ ④字幕 + ⑤出片”。每期都真机验证，杜绝假绿。
